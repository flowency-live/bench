# ADR-0014: Passwordless, invite-only, multi-method auth (the bndy model)

- **Status:** Accepted
- **Date:** 2026-06-27
- **Deciders:** Jason Jones (founder), CTO (Claude)
- **Supersedes:** the **owner email/password** half of [ADR-0012](0012-adopt-cognito-identity-v1.md). Generalises [ADR-0009](0009-admin-auth-magic-link.md)/[ADR-0005](0005-magic-link-sessions.md) (magic-link) to **all** roles.
- **Plan:** `_documentation/auth-redesign-plan.md`. Prior art: `bndy-backstage` / `bndy-serverless-api`.

## Context

ADR-0012 chose Cognito **email/password** for owners. In practice that flow is flaky and user-hostile: the claim form's password rules disagree with the pool's (12 + symbol) and with the error copy ("8 chars"); `SignUpCommand` is non-idempotent so a retry gives "account already exists"; and `signIn` uses `USER_PASSWORD_AUTH` while the pool is SRP-only with self-signup disabled — so the flows contradict the pool and fail differently each attempt.

`bndy` (Jason's proven product) avoids all of this by being **passwordless and multi-method** (phone OTP, email magic link, Google, Apple), with **invite decoupled from auth**: sign in by any method, then accept a held invite. No passwords, no `SignUp`, no `UserExists`.

## Decision

In the context of **owner/admin (and all-role) authentication**, facing **a brittle, contradictory Cognito password flow**, we decided to adopt **passwordless, invite-only, multi-method auth — Email magic link, Phone OTP, Google, Apple — all converging on our `bench_session` cookie, with invites decoupled from sign-in**, and neglected **Cognito passwords and self-sign-up**, to achieve **a slick, idempotent, proven sign-in (the bndy model)**, accepting **more IdP + SMS infrastructure and that Cognito now only brokers *social* identity, not passwords.**

### Methods (one tabbed `/login`, all invite-only)
- **Email magic link** (primary) — our existing `MagicLinkRepository`/GSI3/SES; idempotent verify mints the session.
- **Phone OTP** — Pinpoint/SNS SMS, 6-digit, 5-min TTL (mirrors bndy `/auth/phone/*`).
- **Google / Apple** — Cognito IdPs. Federation proves identity; we then mint `bench_session`.

### Invite-only & generate-and-share
- **No identity gets in** without an existing tenant binding **or** a valid invite token held during sign-in. Unknown + no invite → rejected ("invite-only").
- **Invite = a single-use, tenant+role-scoped link.** godmode → tenant admin; tenant admin → consultant.
- **Generate-and-share:** the generator returns the link with **Copy / WhatsApp / Email / SMS** (+ native share). Not auto-email-only — owners/godmode share it themselves (not forced from `opstack.uk`).
- **Decoupled claim:** sign in by any method, then the held invite token binds tenant + role + activates (`bindIdentity` records the social/cognito id). This removes the brittle "magic link = auth + set-password" chain.

### Session
`bench_session` HMAC cookie stays (edge-safe). Magic link + phone need no Cognito; socials use Cognito federation only to prove identity, then we mint the cookie.

### Sign-in security model (the guarantee)

Two link types, one gate:
- **Invite link** — single-use *enrolment*; the **only** way to bind a new identity to a tenant + role. Generated by godmode (→ admin) or an admin (→ consultant), shared by any channel.
- **Sign-in link / OTP / social** — for an **already-bound** identity proving control of it. A returning admin self-serves at `/login`; **no godmode needed on a new device**.

Rules (must be airtight — this is the security boundary now that passwords are gone):
1. **Sign-in resolves to an existing binding.** A magic link / OTP / social grants a session **only if the verified identity matches a bound, active user**. **Requesting a sign-in link for a non-bound email is a no-op** — neutral response, nothing sent. No invite ⇒ no entry.
2. **Social matches by *verified email*.** Google/Apple/LinkedIn succeeds only if the provider's *verified* email equals a bound user's — it must be *their* account, not any account. (Phone OTP binds a phone number; a user only gets phone sign-in once a phone is added to their record.)
3. **Account access == control of the bound identity** (email inbox / phone / linked social). Requesting a link sends it to the *owner's* inbox, never the requester. Same root of trust as any reset-link/SSO product, and stronger than passwords (nothing weak/reused/phishable to steal).

Controls: godmode/admin can **resend a sign-in link** to a bound user (convenience/recovery) and **revoke/deactivate** a user (removes the binding → every method stops working). Optional per-tenant hardening (CP4): require MFA, restrict to a verified email domain, or social-only.

## What is removed
`auth/claim` set-password, `cognito.signUp/signIn/changePassword`, the password fields on `/login`, and **`/forgot-password` + `/reset-password`** (nothing to reset). The Cognito **pool stays** (ADR-0012) as the social-federation broker.

## Consequences

**Good:** kills the entire class of password bugs; one slick multi-method screen; idempotent; matches a product Jason already trusts; invite links are shareable however the sharer wants.

**Costs / risks:** Pinpoint/SNS SMS (cost + UK sender setup) for phone OTP; Cognito retained but reduced to social brokering; **invite-only enforcement must be airtight** at every entry point (the security boundary moves from "password" to "valid invite or existing binding"). MFA/rate-limiting on OTP + magic-link request stays as hardening (CP4).
